# WebSocket protocol

Connect to `/api/rooms/{roomId}/ws` with the session cookie. The server sends and broadcasts `snapshot` messages. Commands use `{ "type": "player.play", "requestId": "...", "expectedRevision": 3, "expectedPlaybackRevision": 2, "payload": {} }`; failures use `error` messages. Every state-changing command contains the latest room-wide `expectedRevision`. Order-dependent commands (reorder, shuffle, skip, member and access management, transfer) reject stale revisions. Independent intents — `queue.add`, `queue.play_now`, `queue.remove`, `queue.vote`, `queue.vote_skip`, `queue.loop`, `room.sponsorblock` and `room.rename` — apply regardless of the revision, so a simultaneous play, seek or join never makes adding a video fail. Player commands additionally carry the separate playback revision, so unrelated queue, participant, title, or activity updates cannot invalidate a simultaneous play, pause, seek, or rate change. Older clients without `expectedPlaybackRevision` retain room-wide revision behavior.

Automatic end-of-video reports use `playback.ended` with the current internal `mediaId`, playback revision, final position, and finite duration. The server accepts a report only from a member allowed to skip, only while that exact playing media and playback revision remain current, and only for a plausible near-end position. Active capable clients stagger reports by role and identity; the first valid report advances the queue and every delayed duplicate becomes stale. Manual `queue.skip` remains separate.

The explicit broken-player action sends `discardCurrent: true`; this prevents an unavailable or non-embeddable video from being inserted into the queue again when queue looping is enabled.

Non-empty `requestId` values are idempotency keys scoped to `(roomId, identityId)` and retained for 24 hours. A committed retry returns the current snapshot without applying the command again. Reusing a key for a different command returns `request_id_conflict`. Empty request IDs remain accepted for older clients and do not receive deduplication.

Rooms carry `slug`, `mode` (`party`, `cinema`, `host`), `waitForAll`, `countdownSeconds` and `scheduledAt` (Unix ms), changed by managers with the revision-free commands `room.slug`, `room.mode`, `room.wait`, `room.countdown` and `room.schedule`. A mode only sets member defaults; explicit per-member permissions still win. `GET /api/room-links/{slug}` resolves a short link to a room ID. New videos and `player.play` with `countdown` anchor playback in the future: while `playback.startsAt` (server ms) lies ahead, clients hold at `playback.position` and start together. `player.pause` with `reason: "wait"` sets `playback.autoPaused`; the first connected controller resumes it once nobody is buffering. Reactions also carry the current `mediaId` and a 5-second `bucket`; a `heatmap` message on connect replays the in-memory counts for the current video. Account holders manage saved queues through `GET/POST /api/account/queues` and `DELETE /api/account/queues/{id}`; managers list bans with `GET /api/rooms/{roomId}/bans`.

Snapshots include `serverTime` (Unix ms) — the server clock at which `playback.position` was extrapolated. `GET /api/time` returns `{ "now": <Unix ms> }`; clients sample it to estimate their clock offset and anchor positions on the server clock, so network latency does not become a per-viewer offset. Playback timestamps are stored with millisecond precision. Reactions accept a fixed palette of ten emoji and include the sender's `identityId`.

REST responses include a `code` and the `X-Request-ID` response header. HTTP access logs contain the method, normalized route, status, response size, and duration; room and identity identifiers are hashed. The optional authenticated `GET /api/admin/metrics` endpoint exposes process-lifetime counters for HTTP requests/errors, accepted/rejected commands, WebSocket opens/closes, and full outbound WebSocket queues. Logs and metrics never contain command payloads, cookies, secrets, or raw room/identity IDs.

The server negotiates per-message WebSocket compression, sends a ping every 25 seconds, and requires pong traffic within 70 seconds. It revalidates the backing session before every command and closes the socket when the session expires, is logged out, is revoked, or is invalidated by a password change. Non-reaction commands are limited to 180 per minute per socket and per identity. Reactions have an aggregate per-identity limit. Each room accepts at most three connections per identity/session, and each client IP accepts at most twelve connections across rooms. Outbound messages use bounded per-client queues; a slow client is disconnected instead of blocking room-wide fan-out.

Snapshots are personalized per WebSocket client through the `me` identity field. REST management endpoints provide account room listing, room deletion/leaving, private invitations, profile/password changes, active-session revocation, and account deletion. Ownership transfer is the revision-protected `room.transfer` command and requires an account-linked target member. A room accepts at most 100 active identities and 100 queued videos; historical memberships do not consume active capacity.

`queue.add` accepts `{ "videoId", "start"?, "position"? }` or `{ "items": [{ "videoId", "start"? }], "position"? }` for up to 100 videos at once; duplicates in the batch or room are skipped, and `position: 0` inserts at the top ("play next"). `start` is the queued start time in seconds (from `?t=` links). When nothing is playing, the first added video starts immediately. Fresh rooms start empty. `queue.vote_skip` toggles the viewer's vote to skip the current video; a majority of connected people skips it, and snapshots expose `playback.skipVotes`, `skipNeeded` and the personalized `skipVoted`. `room.rename` sets or clears (`""`) a custom room name of up to 60 characters; managers only. Queue items include `addedBy` and `start`.

Rejections carry a stable `code` and a human-readable message, for example `already_queued`, `queue_full`, `stale_revision`, `permission_denied` or `account_required`.

Queue commands also include `queue.vote`, `queue.shuffle`, and `queue.loop`. Votes determine which queued item is selected next, with manual position as the tie-breaker. Snapshots expose vote totals, the current viewer's vote, loop state, and the latest 20 played media items. Duplicate current or queued media is rejected.

`chat.send` (`{ "text" }`, at most 500 characters) is a WebSocket-only message. Chat is ephemeral: the last 60 messages live in server memory, are replayed to joiners as `chat.history`, are fanned out as `chat`, and are dropped when the last viewer leaves or the server restarts. Chat is never written to SQLite, logs or activity. It requires the `chat.send` capability, which managers can revoke per member ("mute"), and is rate-limited per connection and identity. `presence.state` (`playing`, `paused`, `buffering`, `blocked`, `idle`) reports the viewer's local player state; changes are relayed as `presence`, and joiners receive `presence.all`. Presence is also memory-only.

`reaction.send` is a revision-free WebSocket message with one allowed emoji. Reactions are rate-limited per connection and identity, broadcast as transient `reaction` messages, and are never written to SQLite or room activity. `POST /api/rooms/previews` accepts at most five room IDs and returns metadata only for rooms associated with the authenticated identity or account; it does not join rooms.
